# Пускалка

Серверное ядро для лабораторий будущего Moodle-плагина, выделенное из UNetLab.
Одна попытка выполняется одним Docker-контейнером: все QEMU/KVM-ноды и вся
внутренняя сеть лаборатории находятся на одном бате.

Пускалка доверяет менеджеру и исполняет его билет с `.unl`. Пользователь видит
заданную топологию в Moodle и работает с консолями; редактирование топологии
остаётся за пределами исполнителя. В пускалке нет пользователей, авторизации,
локальной БД, веб-интерфейса UNetLab и Guacamole.

## Что выделено из исходного проекта

- Описание нод, ресурсов, интерфейсов и сетевых сегментов `.unl`.
- Профили QEMU, выбор модели NIC и контроллеров по именам дисков.
- Разностные qcow2 от неизменяемых шаблонов; повторный запуск использует прогресс.
- TAP и bridges, MTU 9000, настройки для служебных L2-кадров и коротких сегментов.
- Начальные конфигурации через ISO/FAT для поддержанных сетевых образов.

Старые PHP/C-обёртки заменены небольшим исполнителем Python 3 без внешних
Python-зависимостей. QEMU запускается отслеживаемым процессом; QMP управляет
его жизненным циклом. Состояние нод определяется по процессам, а не открытым
портам. Неудача одной ноды отражается в статусе и не завершает остальные.
Исходный код сохранён в истории Git; связь с ним описана в
[docs/upstream.md](docs/upstream.md).

## Контейнер и билет

```sh
docker build -t puskalka:local .
docker run --rm --mount type=bind,src=/absolute/ticket-directory,dst=/ticket,readonly \
  puskalka:local validate --ticket /ticket/ticket.json
```

Для проверки билета достаточно его JSON и `.unl`. `plan` дополнительно требует
каталог образов, но не создаёт диски и сети. `run` исполняет билет.

Пример билета и лаборатории находятся в [examples/](examples/). Гостевые образы
нужно предоставить отдельно: пример ожидает `/templates/linux/v1/virtioa.qcow2`.
В штатном контейнере доступны QEMU `x86_64` и `i386`; KVM обязателен.

Для запуска батя передаёт `/dev/kvm`, `/dev/net/tun`, `NET_ADMIN` и отдельное
сетевое пространство контейнера. Нужен совместимый с UNetLab режим передачи
служебных L2-кадров в ядре бати: стандартное ядро может запрещать полный
`group_fwd_mask=65535`, и тогда пускалка явно откажет в запуске. Права контейнера
не заменяют эту возможность ядра. Исторический патч сохранён как справочный
материал; применять его автоматически пускалка не будет.

[compose.example.yaml](compose.example.yaml) показывает необходимые mounts и
права. Менеджер бати задаёт лимиты CPU/RAM для всей лабы с накладными расходами.
Docker socket контейнеру не нужен.

## Постоянный прогресс

Менеджер передаёт каталог конкретной попытки из пользовательского хранилища.
Для пускалки это обычный mount; структура личных каталогов плагина и настройка
CephFS относятся к внешнему слою.

```text
/templates/<образ>/<версия>/*.qcow2   неизменяемые шаблоны, read-only
/progress/nodes/<id>/*.qcow2         постоянные разностные диски
/run/puskalka/                      временные QMP-сокеты и логи процессов
```

В `/progress` сохраняются также начальные конфигурации/носители и небольшой
маркер идентичности попытки с хешем определения. Маркер не содержит топологию
и не является БД. Он предотвращает случайное использование прогресса другой
попытки. После остановки/падения контейнера диски остаются; автоматического
сброса, удаления прогресса и сохранения RAM нет. Менеджер обеспечивает одного
активного владельца, прежде чем поднимать замену на другом бате.

## Управление и смотрелка

Внутренний HTTP API для доверенного менеджера:

| Запрос | Действие |
| --- | --- |
| `GET /health` | Доступность исполнителя |
| `GET /status` | Статус попытки и процессов нод |
| `GET /consoles` | VNC/Telnet-подключения для смотрелки бати |
| `POST /nodes/<id>/start` | Запуск ноды с её существующими дисками |
| `POST /nodes/<id>/stop` | Остановка ноды |
| `POST /stop` | Остановка всей пускалки с сохранением прогресса |

`guacd` и веб-туннель Guacamole размещаются на бате и подключаются к адресам
консолей из API. Права учащегося и доступ браузера проверяются Moodle и
менеджером. Подключения и API пускалки предназначены для внутренней управляющей
сети; Compose не публикует их порты на хосте.

KEMU агент внутри гостя и команды для автопроверки/настройки — отдельный этап.
QMP в этой ветке управляет процессом QEMU и не требует гостевого агента.

## Проверка

```sh
PYTHONPATH=runner python3 -m unittest discover -s tests -v
```

При наличии QEMU тесты дополнительно проверяют настоящие qcow2, сохранение
изменений, QMP, VNC и ввод клавиатуры/мыши. Интеграционные тесты используют TCG
и не подтверждают KVM либо L2-связность на ядре бати. Эти проверки выполняются
на целевом хосте с предоставленными устройствами.
