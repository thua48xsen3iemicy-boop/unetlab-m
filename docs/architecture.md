# Пускалка: исполнение одной попытки лаборатории

Ветка `puskalka` выделяет из UNetLab движок запуска лаборатории. Один контейнер
исполняет одну попытку целиком: запускает все QEMU/KVM-ноды, создаёт их TAP и
сетевые сегменты, подключает постоянные диски и сообщает состояние менеджеру.
Исходный проект остаётся доступен в истории Git и исходной ветке.

## Кто за что отвечает

**Moodle-плагин** показывает заданную топологию и консоли. Учащийся работает
внутри нод, но не редактирует состав лаборатории и связи между ними.

**Вышестоящий менеджер** определяет попытку и пользователя, выбирает батю,
подготавливает билет и подключает каталог прогресса. Он обеспечивает единственного
владельца попытки, выдаёт доступ к консолям и собирает состояние выполнения.
Его реализация и интеграция с Moodle относятся к следующим этапам.

**Батя пускалок** — вычислительный сервер, на котором менеджер запускает
контейнеры. Он учитывает CPU, память всех нод, накладные расходы QEMU и самой
пускалки. Лаборатория должна целиком помещаться на выбранном бате. Доступ
к Docker остаётся у бати: Docker socket не монтируется в пускалку.

**Пускалка** доверяет билету менеджера и исполняет его. В ней нет Moodle
авторизации, пользователей, POD, SQLite, редактора топологии, веб-интерфейса
UNetLab или базы Guacamole. HTTP API предназначен для доверенной сети менеджера;
его нельзя открывать учащимся или в Интернет без внешнего контроля доступа.

## Описание лаборатории и временное состояние

Билет ссылается на `.unl`, профили нод и неизменяемые образы. `.unl` определяет
ноды, ресурсы, интерфейсы и подключения к сетевым сегментам. Профили задают
поддерживаемые особенности QEMU для выбранного типа ноды. Билет описан в
[ticket.md](ticket.md).

Пускалка читает это описание, создаёт сеть, готовит диски и запускает процессы.
Локальная редактируемая копия лаборатории и БД для её хранения не нужны.
Сведения о процессах, QMP-сокеты и другие служебные файлы находятся в
`/run/puskalka`; TAP и bridges принадлежат сетевому namespace контейнера.
Менеджер получает текущее состояние через API.

Первый вариант поддерживает QEMU/KVM на x86 с Linux bridges и TAP. IOL,
Dynamips, Docker-ноды и автоматическое применение старых конфигурационных
скриптов UNetLab не входят в этот этап. Поддержка конкретного образа зависит
от его профиля и совместимости с поставляемой версией QEMU.

## Диски и прогресс

Сервис работает с уже предоставленными каталогами. Способ подключения CephFS
здесь не определяется. Менеджер передаёт пускалке каталог прогресса конкретной
попытки внутри личного хранилища пользователя; структура всего личного
хранилища остаётся обязанностью будущего плагина.

В контейнере шаблоны монтируются в `/templates` только для чтения, а каталог
попытки — в `/progress` для записи. У каждой ноды свой подкаталог с разностными
qcow2. Исходные семейства имён дисков UNetLab: `hd*`, `virtio*`, `virtide*`,
`lsi*`, `megasas*`, `scsi*`. Реальная поддержка контроллера определяется профилем
и runner, а не одним наличием файла с подходящим именем.

Overlay создаётся, только если его ещё нет. При повторном запуске используется
существующий диск: остановка и удаление контейнера не удаляют прогресс и
не пересоздают overlay. Шаблон и его версия должны оставаться неизменными,
а абсолютный путь backing-файла внутри контейнера — одинаковым на всех батях.
Обновлять шаблон на месте нельзя: новые версии получают отдельный каталог.

Один каталог попытки одновременно обслуживает только одна пускалка. Пускалка
может защищаться локальным блокированием, но выбор владельца между серверами
и принудительное прекращение старого экземпляра обеспечиваются менеджером.
После сбоя менеджер сначала исключает работающий старый экземпляр, затем
запускает новый с тем же билетом, путями и каталогом прогресса.

Сохраняется дисковый прогресс. Состояние RAM и live migration не входят в эту
итерацию. При аварийном завершении гостевые ОС могут потребовать обычного
восстановления файловой системы после отключения питания.

## Сеть лаборатории

Сегмент `.unl` становится bridge, а каждый подключённый виртуальный интерфейс
QEMU получает TAP. Сеть лаборатории целиком находится в namespace одной
пускалки; разные лаборатории могут работать на разных серверах без связей
между пускалками. `network_mode: host` для этой модели не используется.

Для работы нужны `/dev/kvm`, `/dev/net/tun` и capability `NET_ADMIN`.
Полный `privileged` не требуется. Внешние сегменты `pnet*` разрешаются
только явным отображением из билета на уже подготовленные Linux bridges
пускалки с MTU не ниже 9000. Для внешней связности менеджер должен подключить
отдельный uplink к такому bridge; нельзя использовать управляющий интерфейс
контейнера как неявный uplink.

Для лабораторий со STP, LLDP и другими служебными Ethernet-кадрами требуется
прозрачная передача кадров мостом. Оригинальный UNetLab использует
`group_fwd_mask=65535` с изменённым ядром. Обычное Linux-ядро запрещает часть
этих битов. Контейнер использует ядро бати, поэтому Docker-образ это ограничение
не устраняет.

В первой итерации пускалка завершает запуск с явной ошибкой, если ядро не
позволяет установить требуемую маску. Батя должен иметь совместимое ядро;
проверка необходима до эксплуатации лабораторий. Вариант с Open vSwitch
можно рассмотреть позже; он пока не реализован.

## Смотрелка на бате

QEMU предоставляет VNC для графических консолей и Telnet для последовательных
консолей, заданных профилем. `/consoles` возвращает фактический тип и параметры
подключения каждой доступной консоли. Порты привязаны к IP контейнера и
доступны бате через управляющую сеть; их не нужно публиковать на хосте.

Guacamole находится на бате: `guacd` подключается к VNC или Telnet пускалки,
а веб-туннель Guacamole связывает его с JS-клиентом в Moodle. Один `guacd`
не предоставляет HTML или WebSocket: туннель и клиент — отдельные части.
Менеджер связывает консоль с попыткой и проверяет права доступа пользователя.
В данной ветке `guacd`, туннель и Moodle-клиент не поставляются.

## Управление

Предварительная проверка билета и план запуска:

```sh
PYTHONPATH=runner python3 -m puskalka plan --ticket /ticket/ticket.json
```

Исполнение с HTTP API:

```sh
PYTHONPATH=runner python3 -m puskalka run --ticket /ticket/ticket.json --listen 0.0.0.0 --port 8080
```

API для менеджера:

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/health` | Проверить доступность процесса пускалки |
| `GET` | `/status` | Получить состояние лаборатории и нод |
| `GET` | `/consoles` | Получить параметры VNC/Telnet-подключений |
| `POST` | `/nodes/<id>/start` | Запустить остановленную ноду |
| `POST` | `/nodes/<id>/stop` | Остановить ноду, сохранив её диски |
| `POST` | `/stop` | Остановить попытку |

Пускалка должна отслеживать все процессы QEMU. Завершение отдельной ноды
отражается в статусе и не должно останавливать остальные. `SIGTERM` запускает
корректное завершение процессов. Менеджер должен предоставить время на
остановку до принудительного удаления контейнера.

**KEMU агент** — принятое название QEMU Guest Agent в этом обсуждении.
Он работает внутри гостевых нод; запуск команд для настройки и автопроверки,
а также проксирование обращений менеджера через пускалку обсуждаются отдельно.
На этом этапе интеграция агента не реализуется.

## Сборка и запуск контейнера

```sh
docker build -t puskalka:local .
```

[compose.example.yaml](../compose.example.yaml) показывает контракт запуска.
Нужно задать `TICKET_DIR`, `TEMPLATES_DIR`, `PROGRESS_DIR` и
`MANAGEMENT_NETWORK`. Последняя переменная указывает на уже созданную сеть,
в которой работают менеджер и смотрелка бати. Каждая попытка запускается
отдельным Compose project или эквивалентным вызовом API Docker.

Корневая файловая система контейнера доступна только для чтения. Временные
файлы используют tmpfs `/run` и `/tmp`; постоянные изменения пишутся только
в подключённый каталог прогресса. Лимиты ресурсов задаёт батя на основании
полного билета, а не статического универсального лимита из примера.
